# プロジェクト要約レポート（設計レビュー用）

**対象**: Kintore（筋トレログアプリ）  
**目的**: ChatGPT 等への設計レビュー依頼時に渡す「構造・要点・問題点・改善余地」が分かる要約  
**作成方針**: 事実ベース、コード全文は掲載せず必要最小限の抜粋に留める

## 2.1 プロジェクト概要

### アプリの目的
- **「最短で記録できて、前回より少しだけ良くする筋トレログアプリ」**
- ジムで片手で素早く記録できること、前回値・PR・推移が見えること、継続しやすいことを価値とする。
- ターゲット: 初心者〜中級者。高機能アプリより入力負荷を下げ、前回比較で「次をどうするか」を判断しやすくする。

### 実装済みの主要機能
- **記録**: ワークアウト記録（種目・重量・回数・セット・メモ・開始/終了時刻）、セット種別タグ（ウォームアップ/Failure/ドロップ）、RPE、セット完了チェック、セットのスワイプ削除
- **種目**: 種目マスタ（プリセット・カスタム・部位/器具タグ・検索・お気に入り）、種目ピッカー
- **前回参照**: 前回の重量・回数・セット表示、前回値コピー、+rep / ±2.5kg クイック入力、PR表示
- **ルーティン**: テンプレ保存・種目並び替え（ドラッグ＆ドロップ）・追加・削除、前回ルーティンで開始
- **休憩**: 休憩タイマー（セット完了時自動開始、手動スキップ/延長）、種目別・ウォームアップ/本番の休憩時間分離、フルスクリーン休憩表示
- **履歴**: 日付別一覧、カレンダー、セッション詳細、共有
- **統計**: ワークアウト回数（今週/今月/全期間）、総挙上重量、月間ボリューム比較、連続実施週、PR履歴、部位別実施回数、週別部位別ボリューム、種目別詳細（推移・推定1RM・PR）
- **設定**: 休憩デフォルト、重量単位（kg/lb）、テーマ、再開リマインド・週次サマリ通知、種目・ルーティンへの導線、CSVエクスポート、プレミアム（買い切り・iCloud同期・グラフ全期間等）
- **その他**: オンボーディング、Widget、Watch アプリ（休憩表示・セット完了連携）

### 未実装だが予定されている主要機能（要件定義・プランより）
- 重量・回数の**ピッカー入力**（現状は TextField のみ）
- **プレート計算**・バーベル重量考慮
- **ウォームアップセットの一括追加**（目標重量からの段階的提案）
- **時間（duration）種目**・**アシスト自重**など種目タイプの拡張
- **スーパーセット**（2種目をグループ化）

### アプリの中心価値（現時点の実装ベース）
- 記録画面で前回・PRが常に見え、前回コピー・クイック増減で入力タップ数を減らしている。
- 休憩タイマー・種目並び替え・セット種別/RPE で STRONG.app に近い入力体験を提供。
- 永続化は SwiftData（オフライン完結）。プレミアムで iCloud 同期を有効化する設計。

## 2.6 状態管理の流れ

- **Observable**: HomeViewModel, WorkoutRecordViewModel, WorkoutStartViewModel, HistoryListViewModel, ExercisePickerViewModel, RestTimerManager, PremiumService が `@Observable`。StateObject は未使用。EnvironmentObject は未使用。
- **ViewModel の保持**: HomeView / WorkoutStartView / WorkoutRecordView / HistoryListView はいずれも `@State private var viewModel: XxxViewModel?` で保持し、onAppear または createViewModelOnce で 1 回だけ生成。ContentView 経由で modelContainer が渡るため、View 内で Repository を new して ViewModel に渡している。
- **データ更新→UI**: ViewModel のプロパティ（draft, recentSessions 等）を更新すると @Observable により View が再描画。永続化は「保存」操作で Repository を経由し、保存後に onSaveSuccess で画面を閉じるか、Home 側で loadRecentSessions で再取得。
- **単一責任**: 記録画面は WorkoutRecordViewModel に責務が集中（draft 操作・前回/PR・保存・PR 更新・休憩開始・メモ・進歩提案）。統計は View に @State が多く、ViewModel がなく計算が View と Service に分散。
- **双方向・過多**: WorkoutRecordView は draft を ViewModel 経由で編集し、SetRowView には Binding を渡す。RestTimerManager は WorkoutRecordView が @State で持ち、ViewModel に weak で渡して startRest を呼ぶ形。依存の向きは一方向だが、記録 ViewModel の責務過多は懸念。

| **WorkoutStatsService** | セット/種目/セッション/期間の総挙上、ワークアウト回数、部位別セッション数、週別部位別ボリューム、連続実施週、月間ボリューム | ModelContext, 日付範囲等 | 数値・タプル配列 | Home（週サマリ・ストリーク）、Statistics（回数・総挙上・月間・ストリーク・部位・週別ボリューム）、SessionDetail（セッション総挙上） | ストリークが StatisticsView.load() 内で自前実装されており currentStreakWeeks と重複 |
| **WorkoutSet.volume** | 1セットの volume = weight × reps | weight, reps | Double | 主に内部・PR 判定と別定義 | PersonalRecordService / WorkoutStatsService と式は同じだが実装が分散 |
| **PersonalRecordService** | PR 更新要否、updateIfNeeded（volume 比較で上書き） | exerciseId, weight, reps | Bool / 更新後 PR | 記録画面 PR 表示、保存時の PR 更新、ExerciseDetail | 特になし |

- **volume の扱い**: WorkoutSet.volume、WorkoutStatsService.volumeForSet / totalVolume、PersonalRecordService 内の volume で同じ「weight*reps」が複数箇所にある。仕様は統一されているが重複実装。

## 2.8 永続化・保存方式

- **SwiftData**: メインの永続化。ModelContainer は KintoreApp で ModelContainerFactory.makeProduction() により作成。スキーマは Exercise, WorkoutTemplate, WorkoutTemplateItem, WorkoutSession, WorkoutExercise, WorkoutSet, MemoTag, PersonalRecord, UserPreference。本番では PremiumService.cachedIsPremium が true のとき iCloud  private DB を有効にする設定。
- **UserDefaults**: 休憩タイマー目標時刻、weightUnit 表示用（AppTheme.weightUnitStorageKey）、テーマ（app_theme）、オンボーディング完了・初回起動・レビュー依頼済みフラグ等。AppBootstrapper で UserPreference 作成時に weightUnit を UserDefaults に同期。
- **保存責務**: セッション保存は WorkoutRepository.saveSession(from:exerciseLookup:template:)。PR 更新は WorkoutRecordViewModel.saveSession() 内でループして PersonalRecordService.updateIfNeeded。設定は SettingsRepository が UserPreference を更新し、重量単位はさらに UserDefaults と Export/表示用の AppStorage と同期。
- **スケール時の懸念**: SwiftData スキーマ変更時のマイグレーション方針が明文化されていない。iCloud の ON/OFF 切り替えはコンテナ再作成が必要で、起動時のみのため中途での切り替えは考慮されていない可能性。

## 2.9 UIコンポーネント設計

- **再利用コンポーネント**: SetRowView, SectionCard, SectionHeaderView, PrimaryButton, SecondaryActionButton, MetricChip, InlineStatView, EmptyStateView 等。AppTheme で余白・角丸・色・フォントを統一。
- **共通化**: ボタン・カード・見出しはコンポーネント化。数値表示は AppFormatters と weightUnit の組み合わせ。記録画面のセット行は SetRowView に集約され、種別・RPE は optional Binding で列の有無を切り替え。
- **重複の有無**: カード状のブロックは SectionCard で統一されている。似たリスト行は History と Home のセッション行で似たレイアウトがあるが、同一コンポーネントにはなっていない可能性。
- **デザインシステム**: AppTheme が事実上のデザインシステム。色・フォント・余白・角丸が一括定義されている。コンポーネントが AppTheme を参照しているため、テーマ変更は一箇所で効く。

## 2.10 現時点の問題点・技術的負債

- **View の肥大化**: WorkoutRecordView は 500 行超。StatisticsView も 200 行超で、セクションが多く load() が長い。SessionDetailView は shareText 等のロジックを View 内に持つ。
- **ViewModel の責務過多**: WorkoutRecordViewModel は draft 操作・前回/PR・保存・PR 更新・休憩開始・メモ・進歩提案・クイック入力・Watch コールバックを担当。分割（例: 保存・PR 専用、休憩専用）の余地あり。
- **計算ロジックの分散**: volume 計算が WorkoutSet、WorkoutStatsService、PersonalRecordService に存在。ストリーク計算が WorkoutStatsService.currentStreakWeeks と StatisticsView.load() 内のループで二重実装。
- **命名・統一**: 概ね統一されているが、「RepLog」と「Kintore」の表記が混在（Home のタイトルは RepLog、アプリ名は Kintore）。UserDefaults キーが "kintore.*" と "weight_unit" 等で混在。
- **一時しのぎ**: 重量単位は UserPreference と UserDefaults と @AppStorage の三箇所で同期する設計。AppBootstrapper と設定保存の両方で同期しているため、経路が分かりにくい。
- **将来破綻しそうな箇所**: 記録 ViewModel に機能を追加し続けるとさらに肥大化。Statistics に ViewModel を導入せず @State で持つと、フィルタや期間変更のテストがしづらい。ModelContainerFactory が起動直後の PremiumService に依存するため、Premium の読み込みタイミング次第では iCloud 有無がずれる可能性（要確認）。
- **バグの温床**: インデックス多用（exerciseIndex, setIndex）。guard で範囲チェックはしているが、removeSets や moveExercise の組み合わせでずれないか要確認。休憩開始時の「ウォームアップか」判定は setType と defaultRestSecondsWarmUp に依存し、nil 時は 60 秒フォールバック。
- **App Store**: 特になし。fatalError でクラッシュするのは開発時のみ想定であれば許容されるが、ModelContainer 失敗時はユーザー向けメッセージに差し替える検討余地あり。

## 2.11 今後の改善優先順位

- **Phase 1（今すぐ直すべき）**
  - StatisticsView のストリーク計算を WorkoutStatsService.currentStreakWeeks に統一し、二重実装を削除。
  - ModelContainer 作成失敗時に fatalError ではなくユーザー向けエラー表示にするか検討。

- **Phase 2（次の機能追加前に整理すべき）**
  - WorkoutRecordViewModel の責務分割（保存・PR 更新、休憩開始、前回値表示などに分離するか、少なくともメソッド群をファイル/拡張で整理）。
  - StatisticsView に ViewModel を導入し、load とストリーク等の計算を ViewModel に移す。
  - volume 計算を一箇所に集約（例: WorkoutStatsService の静的メソッドを WorkoutSet や PR 更新からも利用するか、共通の VolumeCalculator を用意するか）。

- **Phase 3（将来のスケールを見据えて）**
  - 記録画面の View を「種目カード」「セットリスト」「休憩」「ツールバー」などに分割してファイルを分ける。
  - SwiftData スキーマ変更時のマイグレーション方針をドキュメント化し、必要ならバージョニングを導入。
  - 重量単位の保存・表示・エクスポートの経路を 1 つに整理（UserPreference を Single Source of Truth にし、表示層だけ AppStorage で購読する等）。
